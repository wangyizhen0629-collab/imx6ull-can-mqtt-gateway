## 最终实现

### 协议与解码器

三类标准 DLC-8 帧均采用 Intel 小端：`0x100 VehicleDynamics`、
`0x101 PowerStatus`、`0x102 BodyStatus`。byte 6 是各自独立的模256
`RollingCounter`，byte 7 是 byte 0～6 XOR。多字节布局、factor、offset、单位均只以
`vehicle.dbc` 为准；协议明确是实验用自定义协议，不代表 OEM 或量产车辆协议。

`gateway_vehicle_decode_frame()` 和 `gateway_vehicle_decode_record()` 不分配动态内存，
以 `centi_kph`、`quarter_rpm`、`millivolt`、`tenth_percent` 等整数定点单位保存物理量。
32字节 `decoded_payload` 通过 `memcpy` 访问；未知 ID、错误 DLC 或 XOR 错误会清零
解码区和 M4 状态位，但保留原始 CAN 数据及已有 timestamp 状态。

### STM32 语义车况

STM32 在 CubeMX `USER CODE` 区域实现60秒确定性循环：

1. 0～3 s：熄火停放，驾驶员门打开；
2. 3～5 s：启动并以800 rpm怠速，车门关闭；
3. 5～20 s：线性加速至60 km/h，32%油门，依次升至4挡；
4. 20～40 s：60 km/h巡航，约2200 rpm、18%油门、4挡；
5. 40～55 s：线性减速至0，油门归零并逐级降挡；
6. 55～58 s：停车怠速；
7. 58～60 s：熄火并打开驾驶员门。

模型仅使用整数定点计算，再按 DBC 反向编码；未定义 spare bits 清零。状态与各消息
counter 只在对应 CAN 帧实际发送成功后推进。完整循环里程从123456.7 km增加至
123457.2 km。

## STM32 实物 CAN 证据

最终非覆盖归档为
`artifacts/20260831T111733+0800-m4-stm32-physical-final/`。审计结果：

| 项目 | 结果 |
| --- | ---: |
| `0x100` | 6000帧；平均周期10.000 ms，范围9.926～10.080 ms |
| `0x101` | 600帧；平均周期99.997 ms，范围99.965～100.025 ms |
| `0x102` | 60帧；平均周期999.972 ms，范围999.941～1000.006 ms |
| DBC/场景 payload 差异 | 0/6660 |
| counter/XOR/spare-bit 差异 | 0/6660 |
| CAN RX 增量 | 6740包、53920字节 |
| CAN 错误计数增量 | 0 |
| CAN 状态/速率 | 前后均 ERROR-ACTIVE；500000 bit/s |

RX 统计比 candump 多80包，是统计快照覆盖了 candump 启停外的命令间隙；53920恰为
6740×8，不能据此认定 candump 丢失80帧。三类 counter 序列分别核对；60秒中
`0x100` 和 `0x101` 已观察到回绕，`0x102` 只覆盖0～59，因此不声称其物理回绕已观察。

原始上传目录名以1970年开头，是目标板 wall clock 未初始化造成的，不是实际采集日期。
捕获行为与归档 `main.c` SHA256 所对应模型完全一致，但没有已烧录镜像哈希，因此这是
行为一致性，不是源码—固件的密码学绑定。

项目所有者确认真实 Keil Build 为0 error、0 warning并已 Download。完整原始 Keil
Build/Download 控制台输出没有归档，所以该项只记录为 owner confirmation，不写成
“完整 Keil 日志已保存”。
