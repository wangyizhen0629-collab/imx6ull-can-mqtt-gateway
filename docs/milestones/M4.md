## 实现结果

### 自定义 DBC 和协议冻结

`protocol/vehicle.dbc` 定义三类标准 DLC-8 帧：

- `0x100 VehicleDynamics`：车速、转速、油门、挡位；
- `0x101 PowerStatus`：电压、水温、SOC、故障位；
- `0x102 BodyStatus`：里程、车门、点火状态。

多字节信号全部明确为 Intel 小端，DBC 保存物理缩放、偏移和单位。byte 6 是每类消息
独立的模256 `RollingCounter`，byte 7 是 byte 0～6 XOR。协议文件和说明都明确这是实验
用自定义协议，不代表 OEM 或量产车辆协议。

### 静态 C 解码器

新增 `gateway_vehicle_decode_frame()`、`gateway_vehicle_decode_record()` 和安全读取 API：

- 不分配动态内存，不在接收热路径使用浮点；
- 使用 `centi_kph`、`quarter_rpm`、`millivolt`、`tenth_percent` 等显式定点单位；
- 在原32字节解码区保存 schema version、消息类型、counter、checksum、有效信号 mask
  和24字节消息 union；
- 通过 `memcpy` 写入/读取 `uint8_t decoded_payload[32]`，避免别名、有效类型和对齐问题；
- 以 `_Static_assert` 冻结三个 signal payload 和总结构大小；
- 未知 ID、错误 DLC 或 XOR 错误不会留下旧解码内容，且不会破坏原始帧和 timestamp
  状态。

CAN ID 常量移入独立 `vehicle_protocol.h`，M2 receiver 继续使用同一常量。M4 只提供
解码 API；没有把它接入 ring buffer、生产者--消费者线程、MQTT 或持久化路径。

### 共享黄金向量

`protocol/test_vectors/vehicle_golden.csv` 有20条人工冻结向量，覆盖：

- 三类消息的 counter 0、1、255；
- Intel 小端、缩放、负偏移、bit mask；
- 信号最小值和最大值；
- checksum mismatch、未知 ID 和错误 DLC；
- `telemetry_record` 成功状态位、失败清零和安全读取行为。

C 单测和 `tools/protocol/check_vehicle_dbc.py` 共同读取同一向量文件。后者只使用 Python
标准库，独立解析本项目使用的 DBC `BO_`/`SG_` 子集并计算位提取、物理缩放和 XOR，
防止 DBC 与 C 测试各自维护互不相干的期望值。

此外，C 单测按 M3 固件的 `0x10`/`0x20`/`0x30` 三个 base 和
`(base + counter + byte_index) mod 256` 规则遍历全部 `3 * 256 = 768` 帧，检查解码信号、
counter 和 checksum。M3 中项目所有者确认真实 `candump` 遵循同一规律，因此静态规律
对应关系成立；本轮没有采集新的物理 CAN 帧，不能写成新增解码器已在板端运行。

## 退出判定

**NOT MET。** 主机向量、DBC 交叉检查、边界/错误路径和旧 STM32 全 counter 规律均有
真实 PASS 证据；ARMv7 warning-clean 交叉构建也已完成。但这些向量没有证明 STM32 从
有物理意义的模拟物理量按 DBC 编码。关闭 M4 前必须取得 Windows 新固件的真实 Keil
Build/`candump` 依据，更新物理场景黄金向量并用新 run 复测。新的板端实时解码仍为
`NOT RUN`，禁止宣称 i.MX6ULL 已运行新增解码器或已经形成生产链路。

当前停在 M4 等待 Windows 输入。M5 及后续未实现；进入下一 Milestone 需要用户另行
明确授权。
