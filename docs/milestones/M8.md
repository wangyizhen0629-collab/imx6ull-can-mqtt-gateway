## API、设计与修复

开始前证据`artifacts/20260901T125544+0800-m8-preflight/`对与M7板端运行库SHA256
相同的ARMv7 libmosquitto 2.0.11核对匹配头文件和动态符号。规范要求的
`mosquitto_socket`、`mosquitto_loop_read`、`mosquitto_loop_write`、
`mosquitto_loop_misc`和`mosquitto_want_write`均存在，因此选择实现条件式epoll reactor。

实现由epoll统一等待MQTT socket、eventfd和timerfd：eventfd承载本地操作唤醒，timerfd
周期调用`loop_misc`，socket按`want_write`动态维护EPOLLOUT。M7的单in-flight MID、匹配
PUBACK后推进cursor、spool恢复和transport离线保留durable记录的语义保持不变。

真实Windows预门禁暴露了两个M8缺陷，失败证据没有改写：

1. `artifacts/20260901T143500+0800-m8-windows-reactor-gate/`：连续CAN使consumer没有idle，
   `gateway_mqtt_sink_poll()`得不到调用，Broker恢复后不重连。提交
   `6c2ed510f75fe8dc762e2ac3586c7cc5a750645e`把poll推进加入consume路径并增加连续输入回归。
2. `artifacts/20260901T155449+0800-m8-windows-reactor-fixed-gate/`：consume路径的同步
   `mosquitto_connect()`在Windows丢弃SYN时阻塞内核TCP connect，spool停止增长。提交
   `25681d871a32ed3936962144418058d1af2700b4`改为`mosquitto_connect_async`、deadline和
   reactor驱动状态机，并增加静默TCP listener不发CONNACK的回归；四次consume均低于
   250 ms且不显式poll，pending4、connect attempts大于1。

最终Ubuntu证据
`artifacts/20260901T160813+0800-m8-silent-listener-reconnect-fix-ubuntu/`记录warning 0、
M8 CTest 2/2、全量CTest 17/17、ASan/UBSan M8 2/2、ARMv7构建及ELF/API/RPATH PASS。

## 真实门禁与失败重跑

第三个Windows run
`artifacts/20260901T163809+0800-m8-windows-reactor-async-gate/`完成了硬件断线、自动重连、
SIGKILL、同spool恢复和state重放，但严格validator失败。原因不是产品seq缺失，而是无
持久化Broker重启后gateway先于clean-session subscriber连接：4个batch已获Broker PUBACK
却未被subscriber捕获，后来state重放虽使unique集合覆盖1～22604，低序号首次出现仍乱序。
仓库validator原样exit1，JSONL未排序，validator未放宽，该run保持**FAIL**。

最终门禁为
`artifacts/20260901T170636+0800-m8-windows-reactor-final-gate/`。它使用全新目标板路径和
全新`/dev/root` ext4 spool；测试配置把重连间隔设为合法的20000 ms，在一次async timeout
后重启Broker，并用Broker日志证明subscriber连接行早于gateway连接行、订阅前gateway
PUBLISH为0。该调整只控制测试捕获顺序，未修改源码、生产默认值、Broker persistence、
网络或CAN状态。

## 断线、崩溃与state恢复结果

1. 在线快照证明SHA256固定的binary运行、CAN持续增长且ACK推进。
2. 第一次Broker中断的两份快照中，pending从239增至974；`ack_offset=213120`、
   `ack_seq=2664`和state SHA256保持不变，gateway PID和binary hash不变。日志连续记录
   async reconnect timeout，consumer/spool没有再被connect阻塞。
3. Broker恢复后，同一PID自动连接，cursor推进到`ack_seq=17322`；subscriber已先订阅。
4. 第二次中断中pending从274增至1013，而`ack_seq=19325`和state hash冻结。控制脚本核对
   PID、comm、exe SHA256和本run配置路径后仅执行一次`kill -9`；返回0、进程消失、wrapper
   `wait_exit=137`。kill前捕获到进程消失之间仍有并发CAN写入，因此data增加10条；state
   未推进，不能虚构为data字节不变。
5. Broker/subscriber就绪后，`main2`以同binary/config/spool启动并越过冻结cursor。
   优雅退出summary为`records_acked=4764`、`last_gateway_seq=24089`、pending0、drop0、
   unexpected PUBACK0、exit0。
6. 独立副本把state magic首字节从`0x47`改为`0x00`，data hash不变、state hash改变。
   `state1`安全重放并以`spool_state_recoveries=1`、`records_acked=27434`、
   `last_gateway_seq=27434`、pending0、drop0、unexpected PUBACK0、exit0结束。

`main2`的epoll/wake/timer/socket/read/write/misc计数为3696/47/43/48/47/1/43；`state1`
为3617/135/48/136/135/1/48。两份summary均`reactor_enabled=1`，所有必需真实运行计数
非零。
