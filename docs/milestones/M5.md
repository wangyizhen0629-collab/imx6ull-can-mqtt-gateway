## 实现

### Producer、解码和有界队列

`gateway_pipeline` 接收一个有上界的 source callback。实际 `gatewayd --run-mock-sink`
把它绑定到 `gateway_can_receiver_receive()`，使用100 ms poll 周期，保持 M2 精确标准帧
过滤、DLC 和内核 timestamp 检查。每个通过 M2 原始校验的记录分配 gateway seq，随后
调用 `gateway_vehicle_decode_record()` 校验 XOR 并按 M4 DBC 解码。

只有解码成功的记录才进入 M1 ring buffer。入队使用配置的
`queue_push_timeout_ms`；满队列超时后丢弃新记录并继续接收。CAN receive、decode error、
queue timeout 三类统计保持独立。由于 seq 在解码/入队前推进，checksum 拒绝和 queue
drop 会留下 sink 可观察的 gap，不能被误写成连续成功。

### Consumer 与 mock sink

单 consumer 从 ring buffer 顺序 pop，调用 `gateway_mock_sink_consume()`。mock sink 不做
MQTT、持久化、batch 或复杂序列化，只验证 timestamp/checksum/decode 状态，并统计
consumed、sequence gap、non-monotonic 和 invalid records。CLI 的
`--mock-sink-delay-ms` 只服务故意慢消费者测试。

### 生命周期

`SIGINT`/`SIGTERM` handler 仍只向 nonblocking self-pipe 写入信号值。主线程读取信号后
设置 stop、关闭 queue 并 broadcast；producer 最迟在100 ms receive poll 返回后看到
退出，consumer 按 M1 语义先 drain close 前已经入队的数据。两个线程都 join 后才销毁
queue、mock sink、lifecycle 和 stats。

## 测试结果

### Ubuntu warning-clean 主机

最终 run：`artifacts/20260831T123149+0800-m5-host-final/`。

- GCC 11.4.0、C11、`-Wall -Wextra -Wpedantic -Werror` 构建 PASS；
- 全量 CTest 12/12 PASS，M5 标签1/1 PASS；
- 定时合成源按100/10/1 Hz组成产生111帧，直接运行观测
  `elapsed_ms=990.599`、`queue_drop=0`、`high_watermark=2`、
  `sink_consumed=111`；
- checksum 错误用例确认3条 raw accepted 中2条 decode/入队，错误记录不入队且形成1条
  seq gap；
- 故意过载使用 capacity 4、push timeout 0、sink delay 2 ms；本次直接运行200条输入中
  5条入队/消费、195条 drop、high-watermark 4；
- `SIGTERM` 15 经真实 signal handler/self-pipe 后 producer/consumer 都完成，队列关闭
  并排空。

过载成功/丢弃的具体分配受主机线程调度影响。门禁检查的是策略和计数不变量，不把
`195` 或退出毫秒数描述为产品性能、确定性上界或板端数字。

开发过程 run `artifacts/20260831T123049+0800-m5-host-dev/` 也保留为 PASS，但最终结论
只引用上述 final run。

### 真实 i.MX6ULL 板端功能门禁

最终 run：`artifacts/20260831T132341+0800-m5-board-owner-final/`。该目录保留项目所有者
从目标板拉回的两个原始日志、逐项验证结果、manifest、summary 和 SHA256 清单；没有
改写此前记录板端 NOT RUN 的历史审计 artifact。

- 运行对象 `/tmp/gatewayd-m5` 的板端 SHA256 与交叉构建值一致；
- 基准启动配置为 queue capacity 1024、push timeout 50 ms、sink delay 0。收到3694条
  物理 CAN 输入，全部 decode、queue success、pop 和 sink consume；queue drop、sink
  gap、non-monotonic、invalid 均为0，high-watermark 2/1024；
- 过载配置为 queue capacity 4、push timeout 0、sink delay 20 ms。6532次 queue attempt
  中2970次成功、3561次按“丢弃新记录”策略 drop、1次在退出时看到 queue closed；
  `queue_pop=sink_consumed=2970`、`sink_gap=3561`、high-watermark 4/4；
- 两次日志均先记录 `stop requested by signal 15`，随后才输出最终 summary，证明信号经
  self-pipe 进入正常 stop/close/drain/join 路径；
- 项目所有者确认 STM32 在两个 `gatewayd` 进程启动后才中途开启。因此基准305次、
  过载75次 receive timeout 是此前无输入时的100 ms空闲 poll，不是 queue drop。

上述结果证明真实物理输入的 M5 基准零 queue drop、故意过载策略和 signal 15 正常退出。
它不证明整段64/69秒持续111帧/s：输入并没有覆盖完整进程运行区间。

## NOT RUN 与证据限制

- **LeakSanitizer：NOT RUN**。当前环境的 `ptrace` 限制不支持可信 LSan 结论。
- **CAN 测试前后错误计数：NOT RUN**。板端 run 没有保存 `can_before/after`，不得声称
  CAN error 增量为0。
- **完整进程区间持续111帧/s：NOT RUN**。STM32 中途开启，不能用 summary 的完整运行
  时长计算输入频率或持续运行结论。
- **shell 精确退出码：NOT RUN**。原始日志证明 signal 15 后到达 post-join summary，
  但没有归档 `wait` 的精确退出状态。
- **正确 UTC：NOT RUN**。目标板日志显示1970年，说明 wall clock 未初始化。

若以后需要 CAN 错误增量、精确退出码、持续负载或性能/可靠性结论，必须另行授权并
建立新的唯一 run，在开始前开启 STM32 并保存 `can_before/after`、正确时间源、完整
日志、summary 和 shell 退出状态。不得推测或倒填这些结果。
