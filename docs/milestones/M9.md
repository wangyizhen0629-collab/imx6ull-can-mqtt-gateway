## 实现与设计边界

1. `deploy/init.d/gatewayd`是POSIX/BusyBox ash脚本。BusyBox init通过
   `null::respawn:/etc/init.d/gatewayd supervise`启动前台supervisor；脚本再启动唯一的
   `gatewayd --config ... --run-mqtt`子进程。脚本不命名为rcS自动扫描的`S??gatewayd`，
   避免rcS和inittab重复启动。
2. `deploy/config/gatewayd.env.example`只保存binary/config/run目录和节流参数；真实MQTT
   凭据仍在私有`gateway.conf`，不提交源码。binary、config和run目录必须是绝对路径。
3. 子进程无论正常或异常退出都会重新拉起。连续快速退出达到
   `GATEWAYD_RESTART_LIMIT`后等待`GATEWAYD_COOLDOWN_SEC`；运行达到
   `GATEWAYD_STABLE_SEC`后清零快速退出计数。
4. `restart`向经`/proc/<pid>/cmdline`核验的supervisor发送HUP，由supervisor向子进程
   发送TERM并等待退出，再启动不同PID；该受控重启不计入故障风暴。
5. `stop`在`/var/run`创建临时disabled标记并停止子进程，supervisor保持存活，避免init
   立即respawn；`start`移除标记并恢复。init终止supervisor时TERM会转发给子进程并清理
   PID/lock文件。
6. `deploy/tests/test_gatewayd_supervisor.sh`使用仅属于测试的fake gateway和临时目录验证
   以上状态机。CMake在`BUILD_TESTING`启用时要求主机BusyBox并注册M9标签测试。

选择BusyBox `inittab`而不是未知的镜像外部supervisor，是因为目标规范已确认无systemd，
而BusyBox init是已知基线。该选择仍须在真实目标BusyBox 1.31.1上验证，不能只凭脚本和
Ubuntu BusyBox 1.30.1关闭门禁。

## 真实板端门禁与退出判定

`artifacts/20260901T180003+0800-m9-board-not-run/test_report.md`将以下项目全部标为
`NOT RUN`：目标文件部署、`/etc`备份/安装、inittab reload或reboot、真实开机自动启动、
受控restart、一次目标进程异常终止后的拉起，以及目标BusyBox 1.31.1重启风暴冷却。

原因是当前Ubuntu会话没有目标板登录端点、凭据或已验证的传输路径，不能实际访问
i.MX6ULL；真实地址/凭据也不得从私有历史证据复制进仓库。所需条件是使用项目所有者已
验证的MobaXterm或提供Ubuntu到目标板路径，并在操作前明确批准本次指定`/etc`、init、
reboot和进程控制范围，随后保存脱敏的原始板端证据。

M9的源码、主机、sanitizer和ARM交叉构建均已有真实PASS证据，但计划要求的“开机启动
和异常拉起”没有真实目标板证据，所以M9总门禁只能是 **NOT MET**。本轮到此停止，
不进入M10。
